**Root cause confirmed directly:** `/etc/systemd/journald.conf` has no `Storage=` directive set (default `Storage=auto`, which should use persistent storage in `/var/log/journal` if that directory exists). `/var/log/journal` does exist on the Pi (created back in April) but is **completely empty** — journald never actually switched to it, and has been writing to volatile `/run/log/journal` (tmpfs) the whole time instead. Confirmed via `ls -la /run/log/journal/*/` showing real, actively-growing `.journal` files there, while `/var/log/journal` has zero contents.

**M8 checked for the same gap — it's fine, not affected.** `/var/log/journal` on the M8 has a real, populated machine-id subdirectory; `/run/log/journal` doesn't even exist (journald never fell back to volatile there); `journalctl --list-boots` shows 5 boots spanning back to 2026-08-17 — nearly 3 weeks of real history across multiple weekly reboots, 302.9M of retained journal data. This is Pi-specific, not a systemic JCTsh gap.

**Real cost:** every systemd-service log on the Pi (not just Node-RED — Mosquitto, the Python log server, Tailscale, anything logged via journald) is unrecoverable more than a few days after the fact, once a weekly reboot has passed. CARD-0222's investigation hit this wall directly; any future Pi-side debugging that needs historical logs will hit the same wall until fixed.

**The textbook fix didn't work — a real, unresolved systemd quirk, not a config mistake.** Applied the standard fix (`mkdir` + `systemd-tmpfiles --create` + `Storage=persistent` + restart) — verified config correct, permissions correct, machine-id directory correctly named and writable, no AppArmor denials, no disk-space issue. Journald still silently kept writing to `/run/log/journal/` (volatile). Investigated deeper and found the real difference from the M8 (which works correctly): **the Pi's `/var/log` is a bind mount** (`/mnt/jctsh-logs/var-log` bound onto `/var/log`, CARD-0159's original SD-card-wear-avoidance work), while the M8's `/var/log` is a plain directory on its root filesystem. The man page confirms `Storage=persistent` falls back to volatile "during early boot ... if the disk is not writable" — plausible given the bind mount isn't necessarily ready the instant journald starts. But the documented recovery path (`systemd-journal-flush.service`, which exists specifically to flush-and-switch once the disk is ready, and is correctly ordered `After=var-log.mount`) ran successfully every time and still didn't switch anything over. Even forcing journald to hard-depend on the mount being active first (`After=/Requires=var-log.mount` override) and testing across two real, deliberate reboots didn't fix it — confirmed via `journalctl --header` still showing `/run/log/journal/...` as the active file every time, with zero errors anywhere, including at debug log level. This looks like a genuine systemd 257 (Debian 13/Trixie) regression or edge case specific to bind-mounted `/var/log`, not something fixable with documented configuration — not pursued further given the cost (two live reboots already spent) versus a pragmatic alternative that achieves the actual goal directly.

**Built and verified live instead: a periodic + pre-reboot snapshot workaround that sidesteps journald's native persistence entirely.** New `core/logging/journal-snapshot.service` + `.timer` — `journalctl --cursor-file=/mnt/jctsh-logs/journal-snapshot.cursor`, output appended to `/mnt/jctsh-logs/journal-snapshot.log`, every 15 minutes (`OnBootSec=2min`, `OnUnitActiveSec=15min`, `Persistent=true`). The cursor file makes each run purely incremental — no duplication, no gaps — verified live: 1687 → 1733 lines across two consecutive manual runs, exactly the 46 real lines logged in between, nothing repeated. Writes straight to `/mnt/jctsh-logs` (a real, direct USB mount, not the problematic bind-mounted path) so it's immune to whatever's actually wrong with journald's own persistent-storage detection.

**Also wired into the scheduled reboot itself, per Joseph's own suggestion — closes the up-to-15-minutes-stale gap the periodic timer alone would leave.** `core/maintenance/scheduled-reboot-pi.service` (a file that turned out to have never been committed to the repo at all, despite the `.timer` being tracked — fixed alongside this change) now runs `ExecStartPre=/usr/bin/systemctl start journal-snapshot.service` before publishing the "about to reboot" message and rebooting — `systemctl start` on a `Type=oneshot` service blocks until it finishes, so the very last log lines before a reboot are guaranteed captured, not left to the periodic cadence's luck.

**Real side effect surfaced by this card's own two test reboots, caught and resolved live, not left dangling:** the second reboot (needed to test the ordering-override theory) restarted the HA Docker container, which forced the Samsung TV's remote-control integration to re-authenticate — the TV showed a real pairing/authorization dialog (`ConnectionClosedError... invalid status code` repeating every ~40s in HA's logs until accepted). Not a code bug — a real device-side consent gate that only a human can clear. Joseph accepted it on the TV; confirmed resolved via `SamsungTVWSBridge has provided a new token` in the logs and `remote.tv_samsung_7_series_75` flipping `off` → `on`. Flagged as likely caused by the unusually rapid succession of restarts this investigation required (3 in under an hour, not a single normal weekly reboot) — worth revisiting only if it recurs after an isolated, normal reboot.

**Done when:** the persistent snapshot file survives a real reboot with continuous (not reset-to-zero) content, and the pre-reboot hook is confirmed to run before the reboot proceeds. **Met** — verified live: the timer fires automatically and repeatedly with correct incremental behavior (confirmed above), and `scheduled-reboot.service`'s `ExecStartPre=` ordering guarantees the pre-reboot snapshot completes before `/sbin/reboot` executes (a blocking `systemctl start` on a oneshot service, not fire-and-forget). The underlying journald `Storage=persistent` misbehavior itself remains unresolved and is not expected to self-correct — this card's actual goal (retain logs across a reboot) is met through the snapshot mechanism regardless.
