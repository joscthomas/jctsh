### CARD-0273 · [enhancement] [hike-izer-orchestrator] hike-izer-orchestrator: split print() output into stdout (routine) vs. stderr (worth a look)
**Status:** Done

**Raised 2026-09-14 (Joseph), a direct follow-on from CARD-0270/CARD-0272's investigation.** Once container stdout is durable and queryable (CARD-0272's journald switch), the value of that durability depends on the output actually being distinguishable by kind — today every diagnostic message in the orchestrator is a bare `print()` with no consistent stream discipline, so a future "how often is Nominatim actually failing" query means grepping free text, not filtering.

**Design corrected 2026-09-14 (Claude found a real constraint, checked live before designing around it) — a full Python `logging`-levels scheme (INFO/WARNING/ERROR) was the original plan, dropped in favor of a plain stdout/stderr split.** Checked how Docker's journald driver (CARD-0272) actually maps container output, rather than assuming: it's **binary, not multi-level** — stdout always lands at journald priority 6 (info), stderr always lands at priority 3 (error), regardless of what a Python `logging` call thinks its own level is. A finer INFO/WARNING/ERROR distinction would only become real (filterable via `journalctl -p`) with `systemd.journal.JournalHandler` writing directly to the journal socket, which needs the host's journal socket bind-mounted into the container — real added infrastructure for a distinction that isn't actually load-bearing, since true unrecoverable failures already reach a separate, durable, dashboard-visible channel (`mqtt_log.publish_log("Alert", ...)` + `ha_notify.send_push(...)`) regardless of what journald thinks. Decided: design around the free binary split Docker's journald driver already gives, not a finer scheme that needs new infra to actually work.

**Real categories found, 2026-09-14 (Claude), grepping every print() call site in the deployed orchestrator, remapped to the two-tier split:**
- **stdout (routine):** progress narration (`"Fetching Environmental Data..."`, `"Searching Immich for assets..."`) — useful only while watching live, disposable after.
- **stderr (worth a look):** recoverable/degraded failures (`"Caption failed for X: e"` → falls back to empty caption, `"fetch_hike_photos.py failed -- continuing without photos"`) and retry-attempt failures (`"Step 1 generation failed (attempt 1/3)"`) — code already handles these gracefully or retries automatically, but worth being able to spot a pattern via `journalctl -p err` once CARD-0272 lands.
- **Final/unrecoverable failures** — already correctly durable via `mqtt_log.publish_log("Alert", ...)` — no gap here; the local `print()` alongside it should still go to stderr for consistency, but this tier's real durability doesn't depend on this card at all.

### CARD-0268 · [bug] [pi1] Docker pulls on the Pi can starve HA's own I/O on the shared USB 2.0 bus — real, not hypothetical — RESOLVED 2026-09-14 10:05 MST via CARD-0269
**Status:** Done

**Referrers-hang bug fully resolved 2026-09-14, via CARD-0266's actual apply.** The digest-pull workaround (fix option 5, "pull by exact manifest digest instead of the floating `:stable` tag") was tried and **failed identically** — `docker pull ghcr.io/home-assistant/home-assistant@sha256:a1bc133af84e...` hung the same way, ruling out tag-resolution as the trigger. **The real workaround: containerd's own lower-level CLI, `sudo ctr -n moby images pull ghcr.io/home-assistant/home-assistant:stable`, bypasses the hang entirely.** `ctr` doesn't go through dockerd's own pull orchestration (the code path that gets stuck after the referrers 404 + manifest 404 double-miss) — it talks to containerd directly, correctly recognized all already-downloaded content as "already exists," and proceeded to genuinely extract the one missing layer. Ran for ~50 minutes total (mostly slow extraction off the USB 2.0 bus, not stuck) and completed cleanly — `docker images` picked up the new digest immediately afterward with no further intervention needed.

**Revised procedure for future HA (or any GHCR-image) updates on this Pi, combining both fixes found this session:** don't use `docker pull`/`docker compose pull` at all going forward for images that hit this bug — use `sudo ctr -n moby images pull <image>:<tag>` instead, then `docker compose up -d <service>` to recreate the container on the now-fully-present image (compose correctly picks up content that `ctr` already pulled — confirmed live). This should be the default first attempt now, not a last-resort workaround, since the `docker`-CLI path has a confirmed reproducible hang in this host's Docker 29.6.1 and `ctr` has none of that risk. The I/O-contention fix (options 1-2, ionice + scheduled window) still stands as a separate, complementary concern — it should wrap the `ctr`-based pull, not a `docker`-based one, whenever that scheduling mechanism gets built.

**One more real snag hit during the same apply, worth recording:** after `ctr images pull` finished, `docker compose up -d homeassistant` initially failed (`cannot stop container: tried to kill container, but did not receive an exit event`) — a stale-report race, not a real stuck container (the old container had actually finished exiting a few seconds later). Retrying the same `docker compose up -d` succeeded, but left the new container under a temporary auto-generated name (`<short-id>_homeassistant`) instead of the compose file's `container_name: homeassistant`, because the first attempt had already reserved that name transiently. Fixed with a manual `docker stop`/`docker rename`/`docker start` back to the correct name. Not itself part of the referrers-hang bug — a separate, minor compose-recreate rough edge worth knowing about if it recurs.

**Raised 2026-09-14, from a real occurrence during CARD-0266's HA update attempt.** Pulling the new `homeassistant` image on the Pi caused the *live, already-running* HA container's own health check to start timing out (curl to `/manifest.json` failing at the 10s healthcheck timeout, `FailingStreak` climbing, `docker inspect` showing genuine "unhealthy") while the pull was in progress — confirmed via direct `curl` timing from the Pi itself during the incident, not assumed. Killing the pull immediately restored HA to healthy within about a minute. This is the first real, live confirmation of the shared-bus caveat CARD-0264 already flagged as theoretical ("a new coordinator's traffic and the jctsh-logs drive's I/O would compete on that same shared bus under heavy load").

**Root cause:** the Pi 3B+ has all 4 USB ports *and its onboard Ethernet controller* sharing one internal USB 2.0 hub — a known hardware property of this board, not fixable in software. Docker's data-root also lives on that same USB-attached drive (`jctsh-logs`, moved there deliberately by CARD-0159 to protect the SD card from wear). A pull's network download and layer-extraction writes both compete with HA's own already-mounted config/recorder-DB reads on the identical physical bus — not a coincidence that HA degraded specifically while the pull ran.

**Separately observed, same incident, investigated in full 2026-09-14 — this turned out to be a distinct, unrelated bug, not the same I/O-contention issue.** Pull progress sat at "Pulling fs layer 0B" for 10+ minutes across many attempts, including ones where HA stayed perfectly healthy the whole time (ruling out contention as the cause for *this* symptom) and survived a full host reboot (ruling out stuck daemon/lease state). Root-caused via dockerd's own debug logging (`daemon.json` `"debug":true`, temporarily enabled and reverted): every manual step tested clean and fast via direct `curl` — DNS resolution, the ghcr.io auth token exchange, and the manifest-index fetch all completed in under a second each. The actual hang: after resolving the manifest index, dockerd tries an OCI "referrers" (supply-chain attestation) lookup for one specific sub-manifest digest, gets a `404`, retries it as a direct manifest fetch, gets a second `404` — and then **dockerd's own journal goes completely silent for 5+ minutes with zero further log activity**, every single time. This reproduces cleanly and looks like a real bug in this host's Docker version (29.6.1) triggered by that specific "referrers 404 + manifest 404" double-miss pattern, not a network or resource problem. Confirmed the real image content isn't actually blocked by this — all 6 real layers fully downloaded and verified present in containerd's own content store (hundreds of MB) across the cumulative attempts; only the final tag-update step is stuck behind this one metadata lookup. Not yet fixed — an untried workaround (pulling by the exact resolved manifest digest instead of the floating `:stable` tag, which may route around the referrers-resolution code path) is the next thing to try if this needs solving rather than worked around via scheduling.

**Fix options, not yet decided between:**
1. **`ionice`/`nice` the pull** (idle I/O class) so HA's own small reads get bus priority over the bulk transfer — doesn't speed up the pull, but stops it from starving the live service. Cheapest, most targeted fix for the actual symptom hit.
2. **Only pull during the existing scheduled maintenance window** (Pi reboot, Mon 3 AM) — policy fix, not infrastructure; converts "occasionally degrades live HA" into "happens while nothing's using it." Could be scripted into the existing weekly-reboot automation.
3. **Split Docker's data-root** — keep true persistent state (recorder DB, Mosquitto persistence) on the USB drive per CARD-0159's wear reasoning, but let the image-layer pull/cache itself live on the SD card instead, since pulls are occasional, not the high-frequency-write pattern CARD-0159 was protecting against. Needs care not to undo that protection.
4. **The real architectural fix: move HA off the Pi onto the M8** (NVMe storage, 2.5GbE, no bus-sharing limitation at all) — removes the root cause rather than working around it, but a genuinely bigger change given HA's current tight coupling to Mosquitto/Node-RED (both Pi-native) for low-latency local automation.
5. **For the separate referrers-404-hang bug specifically:** try pulling by exact manifest digest instead of the floating `:stable` tag (untried); or check whether a newer Docker Engine version is available for this Debian/Pi that fixes the underlying bug — this doesn't overlap with fix options 1-4 above, which only address the I/O-contention symptom, not this distinct hang.

**Closed 2026-09-14 10:05 MST — both confirmed real problems this card exists to track are now root-caused *and* mitigated, not just documented.** CARD-0269 built `pi-image-pull.py`, delivering fix option 1 (`ionice`, live-verified) and the `ctr`-based workaround for the referrers-hang bug (fix option 5) as the actual default pull mechanism on this host, plus fix option 2 (`--schedule`) as an available, verified flag — not yet used unattended by choice, but built and proven, not just theoretical. **Fix options 3 (split Docker's data-root) and 4 (move HA to the M8) remain undone, deliberately** — both are heavier architectural changes this card always framed as "revisit if this recurs enough to justify picking one," not pending commitments. With the actual pain point (a hung/contending pull) now addressed by a working, reusable tool, there's nothing this card needs a human decision on right now. If contention or a similar bug resurfaces despite `pi-image-pull.py`, reopen or reference this card rather than starting the investigation over — the root-cause analysis above still holds.
